Every loop, every view shape

Each row increments all 3.6 million elements once. The tick is the same loop over the bare image, so the right-hand figure is what the view costs as a multiple of no view at all. Four loops × six shapes × two image types; the bare image is the tick, not a row.

flat1d {3600000}merge2d {90000,40}split4d {300,300,8,5}identity3d {300,300,40}singleton4d {300,300,1,40}translate3d Views.translate(img,1,2,3)

On ArrayImg the view shape does not matter. flat1d, merge2d and split4d all land within 3.07–3.40 ms for the three cursor loops, although merge2d divides per element and split4d does not. The cost is the cursor layer, not the reshape arithmetic — which is what FlatIndexCursorBenchmark concluded independently.

singleton4d and translate3d now match the genuine reshapes at about 3.2 ms. Both are MixedTransforms, and both take the flat-run path added for order-preserving Mixed transforms.

On CellImg, asking for flat order is not free. With no view, Views.flatIterable costs 16.4 ms against the cell cursor’s 7.75 ms, because it must impose an order the image does not have. Once a reshape is present the view already forces flat order and the two agree at about 19 ms.

randomAccessWalk remains the exception. It calls setPosition with a full position for every pixel, the one pattern an incremental accessor cannot exploit, and costs 4.7× the bare image on ArrayImg. The cause of its gap against the other branch’s TransformRandomAccess is still not identified.

Show the numbers

LoopBuilder against the plain cursor

The clearest new finding in this run, measured against Views.iterable(v).cursor() — the cursor a caller gets without asking for flat order. none and identity3d are the controls: no transform survives in either, and there the two agree. On an ArrayImg they agree for every shape, because LoopBuilder.isFastCursor recognises a FlatIndexCursor whose source is an array cursor. On a CellImg with a real reshape it does not: the flat-run path hands out a FlatIndexCursor wrapping a RandomAccessibleIntervalCursor, which is not on the fast list, so LoopBuilder falls back to its own random-access loop and pays twice over.

view.cursor() LoopBuilder

The gap tracks how much work the fallback accessor does: 2.1× for the three genuine reshapes, 1.42× for singleton4d and 1.23× for translate3d, whose accessors are plain MixedRandomAccesses. With no view at all it is 1.24× with overlapping error bars, and for identity3d, where the transform is deleted outright, 1.16×.

The baseline matters here. Measured instead against Views.flatIterable(v).cursor(), LoopBuilder would look 1.7× faster on an un-viewed CellImg — not because it is quick, but because forcing flat order on a CellImg that needs none costs about 2× by itself (7.75 → 16.42 ms). Through a reshape the two cursors agree to within noise, so for the rows that carry the finding the choice of baseline changes nothing.

This is a LoopBuilder whitelist question, not a reshape one: a caller reshaping a CellImg is better off today writing the cursor loop by hand. Not yet investigated.

Against the September run

Same benchmark, same code, same machine, 54 days apart. Nothing in src/main changed in between except a javadoc edit, so this is a reproducibility check rather than a measurement of any change.

This run is slightly slower across the board — median +2.5%, and 48 of 56 points are above the September value. A uniform shift like that is machine state, not code: this is a 12th-gen mobile i7 with performance and efficiency cores and no pinning, so thermal and scheduling drift of a few percent between sessions is expected. The two points outside ±10% are loopBuilder / CellImg / translate3d (+20%) and flatIterableCursor / CellImg / merge2d (+10.5%), both with error bars wide enough to cover the difference.

How this was measured

source
src/test/java/net/imglib2/view/ReshapeViewBenchmark.java
harness
JMH 1.37 on JDK 21.0.3 (Zulu), average time, 5 × 100 ms warmup, 5 × 200 ms measurement, 1 fork per parameter set, single-threaded
machine
12th Gen Intel Core i7-1280P, 20 threads, 30 GB. Not pinned, not isolated, no CPU governor control
image
300 × 300 × 40 IntType, about 14 MB — out of cache. CellImg cells are 64 × 64 × 8, deliberately ragged against the image
operation
t.inc() per element and nothing else, so the loop and the view are what is timed. No Blackhole: the increments land in the image’s own array, which stays reachable, so they cannot be elided
loops
Views.flatIterable(v).cursor(), Views.iterable(v).cursor(), LoopBuilder.forEachPixel, and a RandomAccess driven over every position by a LocalizingIntervalIterator
self-check
Before timing, all 56 combinations run once over a 5 × 4 × 6 image and every element of the underlying image must be exactly 1. A loop that silently skipped elements would otherwise report a fake speedup. It passed — see the first line of the raw output
caveats
Cursor and loop construction is inside the timed method, so each number includes one TransformBuilder setup amortized over 3.6 M elements. Error is JMH’s 99.9% confidence interval and reaches ±6.9 ms on the random-access rows and ±5.7 ms on CellImg
